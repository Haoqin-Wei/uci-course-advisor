## 已确认的第一版范围

- 使用已购阿里云美国（硅谷）ECS，2 vCPU、4 GiB 内存，网站与用户数据部署在同一台机器。系统建议 Ubuntu 24.04 LTS；部署前核实实际镜像。
- 先邀请几十位同学使用，但不限制邀请名单。注册只接受 `@uci.edu` 邮箱，暂不验证邮箱归属，暂不设置每日提问额度。
- 注册立即保存账号与密码哈希。首次提问、主动保存资料或导入成绩单时，才写入必要的业务记录。
- 注册后可以直接提问；引导填写 Student Profile，可以跳过。
- Student Profile 沿用现有字段和页面：学校、学历、专业、年级、毕业信息、GPA、学分、课程等。
- 回答自动结合当前用户的资料；资料为空时可以正常回答，不能臆造用户信息。
- 保留基础跨对话记忆，后续再强化；明确的本人事实可以直接更新资料，假设、否定、转述、引用及模型猜测不能被当成本人事实。
- 成绩单只保存解析后的学业字段，不持久保存原文件或原始全文。
- 迁移本地已有账号、资料、课程、聊天与关联记忆，保留原有归属关系。

## 推荐的存储结构

第一版沿用项目已有 SQLite 存储及会话文件，先完成一致性、权限、备份与并发验证，不把更换数据库作为上线前提。

这里的“用户数据库”是共享存储：各账号的数据以 `user_id` 关联、由后端鉴权隔离。无需为每个用户创建一个独立数据库、数据表、容器或常驻进程。账号、学业、记忆按业务分库可以继续保留。

| 内容 | 当前默认位置 | 关联方式 |
| --- | --- | --- |
| 账号、密码哈希 | `data/auth.db` | `users.id` |
| 课程、成绩、学分、GPA、导入记录 | `data/academic.db` | `user_id` |
| 用户画像、偏好、事实、来源与更新事件 | `data/memory/long_term_memory.db` | `user_id` |
| 对话、消息、课表、会话状态 | `data/memory/{user_id}/sessions/` | 用户目录及会话元数据 |
| 公共课程、教授、校历等数据 | 现有公共数据目录 | 供用户共享，无需按人复制 |

这些是代码默认位置，不是对当前本地实际运行配置的盘点。迁移时还要核实环境变量覆盖的路径。

数据库表可以在应用初始化时统一建立。“惰性创建”限制的是用户级业务记录。共享数据库文件的存在，不等于每个空账号都占用一套数据库资源。

SQLite 适合低至中等流量网站，但每个数据库文件同一时刻只有一个写者。因此先采用单应用进程，短事务、写入锁及连接超时按实际代码配置，并验证多个浏览器标签页、流式对话、后台记忆和成绩单导入同时运行的行为。单进程本身不能消除异步任务或线程之间的竞争。

以实际并发写入、锁等待与响应时间决定升级时机；未来需要多应用实例或持续高写入并发时，再迁移至 PostgreSQL。注册人数本身不能证明容量足够。

依据：[SQLite 官方适用场景](https://www.sqlite.org/whentouse.html)。

## 用户生命周期与惰性写入

| 用户操作 | 允许的持久化行为 |
| --- | --- |
| 注册 | 账号、密码哈希、协议接受信息及必要认证记录 |
| 登录、刷新首页、读取空资料、打开编辑器 | 返回现有数据或空结构；不创建空会话、画像或用户记忆迁移记录 |
| 仅点击 New chat | 在前端准备空对话，等发送时再创建持久会话 |
| 首次发送消息 | 幂等地建立会话与必要状态，保存消息；有明确事实时才新增画像字段或记忆 |
| 主动保存资料 | 保存提交的资料；不要求必须先聊天 |
| 导入成绩单 | 校验结构化字段后事务写入；重试不重复新增课程或导入记录 |
| 后续提问或更新资料 | 读取当前资料版本，避免旧会话长期沿用过期专业或课程 |

对于现有用户，旧数据迁移应在上线迁移流程中显式执行；不要让新账号仅因首页读取操作就进入旧数据迁移写入流程。通过唯一约束、事务及请求幂等性处理同时首次提问/保存资料，避免依靠内存布尔值防重。

## 个性化回答与记忆更新

请求链路：浏览器提交问题 → 后端从登录会话解析用户身份 → 读取该用户资料、相关记忆和当前对话 → 查询相关公共课程数据 → 组织受控上下文 → 调用现有模型 API → 返回并保存回答。

- 用户标识来自服务端验证过的登录会话，不信任前端传入的任意 `user_id`。
- 密码、密码哈希、登录令牌和验证码不进入模型上下文。邮箱也不作为选课所需画像字段发送。
- 模型按需获得学业信息与相关记忆，不获得通用数据库访问权。记忆中的文字是数据，不能变成新的系统指令。
- 用户资料每轮保持新鲜，可按资料版本缓存；“首次使用才创建”不意味着“资料永远只读一次”。
- 已修课程的完整记录用于先修条件判断，不能只凭随意截断的课程摘要判断是否满足要求。
- 仅明确的本人事实写入正式资料。例如“我已经转成数学专业”可以更新；“如果我转成数学专业”“我朋友是数学专业”“我没有转专业”不能据此把专业改为数学。
- 判断必须针对具体陈述，不能看到整条消息含“如果”就放弃其中所有真实信息。中英文、否定、引用及混合语句都要覆盖。
- 资料更新保留来源消息、时间、旧值及新值，并提供可见的更正/撤销途径。模型推测不能伪装为用户明确陈述。
- 课程状态与成绩单的冲突要记录来源，不能用一条模糊聊天直接覆盖有来源的成绩或 GPA。第一版优先可靠更新明确的身份、目标及偏好字段。
- 保留现有查看/删除记忆与注销账号入口；删除聊天与删除由聊天形成的长期记忆应有清楚的产品说明。

现有成绩单流程已经在浏览器中解析 PDF，仅上传允许的结构化字段。继续采用该方式；文件和原文无需传到服务器再删除，也不应进入日志或备份。

## 资源与滥用边界

惰性创建可以减少空记录和无用初始化，但不能防止攻击者注册后立即发消息。真正需要约束的还有密码哈希计算、模型调用、并发连接与大请求。

遵循暂不设每日额度、暂不验证邮箱的要求，建议保留现有短时请求频率控制，并补全并发生成上限、请求体大小上限、超时/取消、日志轮转及费用告警。这些不等于给正常用户设置每日提问次数。

只检查 `@uci.edu` 后缀无法证明邮箱归属。第一版必须如实保存未验证状态；存在邮箱被冒用或抢注的可能，不应对外声称账户均已验证为 UCI 学生。后续验证与账号归属恢复需要独立流程。

网站以 HTTPS 对外提供服务，应用使用独立系统用户，认证密钥与模型密钥放在服务器环境配置。关闭生产环境共享 demo 与匿名写入，数据库和用户数据目录不通过静态文件服务公开。

## 部署与迁移顺序

1. 按本文完成注册、惰性写入与明确事实更新的必要改动，保留现有学期规则，并运行受影响回归。
2. 为服务器准备固定 Python 3.14.4 环境、应用服务、HTTPS 入口及持久数据目录。代码发布与运行数据分开，更新代码不能覆盖用户数据。单机可先采用系统服务托管应用。
3. 盘点本地实际数据路径、账号 ID 与资料归属，统计各库及会话数量；孤立 demo 数据要明确归属，不能自动开放给所有用户。
4. 首次迁移采用短暂停写/停服务窗口，对全部相关存储制作同一迁移批次的快照，保留原始备份。传输使用受保护的连接，保留原 `user_id` 与密码哈希。
5. 恢复到服务器，执行必要的 schema/旧记忆迁移。生产登录签名密钥单独配置，允许原用户用原密码重新登录；不要求旧浏览器 cookie 跨域继续有效。
6. 在开放前验证账号数量、课程数量、对话关联、登录、跨账号隔离、惰性行为、资料更正、断线重试与重启后的数据持久性；压测实际预期并发。
7. 设置自动备份、失败告警与恢复演练，再邀请第一批同学。建议初始每日一次并在部署前额外备份；如不能接受最多一天的数据损失，应提高频率。

迁移多个数据库及会话目录时，SQLite 单库快照不能自动保证跨库/跨文件的一致时点。首次迁移用停写窗口最容易核对。持续在线备份需使用 SQLite 官方备份机制，并安排跨存储一致性策略，不应随意复制正在写入的 `.db` 文件而忽略 WAL。

依据：[SQLite 官方 Backup API](https://www.sqlite.org/backup.html)。

运行时网站和数据库可以都在这台机器上；备份至少另存一份到机器之外的受控位置。备份应加密并限制访问，设置保留期限；恢复时需要重新应用备份之后已执行的账号删除，避免让已删除数据重新出现。机器外备份不要求购买托管数据库。

## 上线验收样例

- 新注册账号关闭页面：账号存在，但无空画像、课程、会话及用户记忆迁移记录。
- 登录/刷新/打开空 Profile：不触发业务写入或模型调用。
- 第一次提问：可以回答；资料为空时不冒充已知专业或已修课程。
- 先填资料再第一次提问：首条回答使用已保存资料。
- 同时发第一条消息并保存资料：不会重复创建、覆盖或丢失资料。
- “我已经转成数学专业”与“如果我转成数学专业”：前者允许更新，后者保持原资料；中英文、否定、转述及混合句有对应反例。
- 原会话中途更改 Profile：后续回答使用新资料，新会话也一致。
- 账号 A 篡改账号 B 的 user/session 标识：无法读取、修改或删除 B 的任何数据。
- 迁移后原账号可以重新登录，个人资料、课程、聊天、课表和记忆归属一致。
- 应用重启/代码更新后数据仍在；备份实际可以恢复到隔离目录并通过校验。
