# UCI Course Advisor 评测方案讨论稿

日期：2026 年 10 月 24 日。用途：与导师讨论研究问题、标注标准、实验规模和实施顺序。本文提出评测设计，尚未构建最终数据集或运行本轮实验。

研究主线是两层评价：**硬性可行性回答课程能否在给定条件下修读，个人偏好匹配回答学生是否愿意考虑这些课程。** 两层分别报告，并增加一个联合指标，统计最终推荐中同时满足两项要求的比例。系统正确处理未知信息、提供有证据的说明，也是硬性评价的一部分。

建议研究问题如下：

1. 系统能否避免把已知不可行的课程或教学班组合作为可执行方案推荐，并正确处理资料不足、附加条件和无解情况？
2. 在相同可行候选和信息条件下，系统推荐是否比简单排序方法更符合学生偏好？
3. 完整网站自主检索和出卡时，能否同时保持可行性、偏好匹配和证据一致？

## 一 两层评价如何定义

### 硬性可行性

判定单位是“匿名学生、目标学期、评估时刻、课程及具体教学班组合”。同一门课程可能 A 班不可行、B 班可行；讲座合适，也可能因为必选讨论课冲突而整体不可行。除非任务明确要求整套课表，推荐的三门课先视为三个备选方案；只有用户要求一起修读时，才额外检验三门之间的冲突与总学分。

独立标注时，每项条件使用以下真值：

| 真值 | 含义 | 示例 |
| --- | --- | --- |
| T | 在明确评价范围内，证据支持条件满足 | 完整学业记录证明先修已通过，所选完整班次组合不冲突 |
| F | 证据支持条件不满足 | 已确认最低先修成绩不足，所有可用组合均违反用户硬时间要求 |
| U | 关键资料不足，无法判断 | 学业记录不完整、时间 TBA、目标学期查询失败 |
| C | 满足一个尚未实现的明确条件后才可能可行 | 需要许可码、限制尚未解除、在修先修尚待通过 |

合成总体标签时，任一必需项已确认 F，则总体 F；无 F 但有 U，则总体 U；无 F/U 但有未实现条件，则总体 C；其余为 T。保留逐项标签和条件，不能只保存总体字母。

另外记录**系统行为 Pass 或 Fail**，这与课程真值不同。U 时明确说明缺什么、提出相关澄清或暂停正式推荐，可以是行为 Pass；它不代表课程已被证明可选。F 课程作为“建议现在选”的正式项目推出，即使附一句笼统的“请自行核实”，仍为 Fail。

把课程列为未来路线参考、候补选项或待核实候选，应有清楚标签；它们不能计入已核实可行推荐数。所有被提及课程均保留在审查记录中，避免通过更改名称或免责声明隐藏错误。

“可修读”需要拆出三个字段：学业资格、班次组合可行性、当时注册状态。满员不等于永久不能修；候补不等于已有席位；资料齐全的规划建议也不等于实际注册成功。第一版评价承诺范围是**基于快照的规划可行性**，另外报告注册状态，不能把它写成注册成功率。

### 个人偏好匹配

由对应学生评价课程对本次目标的吸引力，采用 `0 不考虑 / 1 勉强考虑 / 2 愿意考虑 / 3 很想选 / U 无法判断`。预先规定 2–3 分为“相关课程”。课程是否满足资格由事实标注决定，不要求学生自己充当资格审查员。

硬条件与软偏好须从原话区分：“周五绝对不能上课”是硬条件；“最好不要早八”是软偏好。不能为了提高偏好分，把软偏好升级为硬排除。

## 二 结合当前系统确定研究范围

现有主流程为 `/api/chat/stream` → 意图解析和工具调用 → 候选检索，以及开关启用时的动态预筛和固定排序 → 推荐与卡片 → SSE 展示、保存和恢复。评价最终用户看到的正文、卡片和选中班次，不能只检查中间 Filter Plan。

| 当前能力或边界 | 对评测设计的影响 |
| --- | --- |
| 动态预筛与固定排序分别有开关，共享默认均关闭 | 每次实验记录实际开关；“研究配置”和当前运行网站配置分别注明 |
| 固定数值排名主要使用历史 A 率和 RMP，默认权重 0.6 与 0.4 | 可以检验这些信号是否符合偏好；不能直接把推荐分当教学质量、工作量或个人得 A 概率 |
| 已有课程年度 GE 证据，但没有完整可信的个人 GE 审计适配器 | “属于某 GE 类别”和“能抵扣此学生剩余要求”分开标注；缺个人审计的正确澄清也要测试 |
| 部分学业档案不能证明先修不满足；在修、已修和课表草案不同 | 测试完整与部分记录、最低成绩未知、在修预计通过和计划课程混淆 |
| 班次配对、TBA、历史数据与目标学期证据存在不同状态 | 测试完整 Lec/Dis/Lab 组合，不用历史教授或班号填补未来事实 |
| 当前检查器不提供通用的个人总学分上限判断，许可与复杂注册限制也需要独立证据 | 测试正确引用、提示与澄清；不能把课表检查 `valid=true` 等同全部资格通过 |
| 已有离线回归、公开资料回放和少量真实模型个案 | 它们可作为开发材料；最终测试需补充未用于调试的新情境与真实学生标签 |

第一版优先覆盖资料较完整的 2–3 个专业及系统已有目标，例如选课时间、专业或 GE 范围、历史给分与教授评价。兴趣和工作量可以作为探索目标收集，但单列结果：目前没有完整的确定性兴趣或工作量排序特征，历史 A 率不能充当工作量真值。

工程依据：[动态预筛](dynamic-prefilter.md)、[固定排名](recommendation-ranking.md)、[学期规范](term-rules.md)、[证据和展示修复](recommendation-f001-f004-2026-10-20.md)。

## 三 测试集的组成和规模

以下数量用于控制第一轮工作量，属于待讨论的探索方案，不代表已经满足统计功效要求。

| 数据集 | 建议规模 | 主要用途 | 划分 |
| --- | --- | --- | --- |
| 硬规则情境集 | 120 个基础情境 | 可行性、未知处理、证据表达与多轮行为 | 40 个开发，80 个封存测试 |
| 学生试调查 | 5–10 名学生 | 修改题目、标签定义、候选资料和实验流程 | 全部开发使用，不混入最终成绩 |
| 学生偏好测试集 | 30 名新学生，每人约 20 门候选 | 偏好排序及最终网站输出评价 | 在方案冻结后收集，全部用于探索性测试 |
| 实时核验子集 | 约 10 个封存情境 | 检查真实外部查询与固定回放的差异 | 单独报告，不增加独立样本数 |

若选 3 个专业，可争取每专业低年级、高年级各 5 人，共 30 人。招募困难时减少专业范围并说明实际人数，不用同一人的多个问题补足独立学生数。转学生单独标记，便于识别抵扣资料缺失造成的困难。

偏好初始标注量约为 `30 × 20 = 600` 个学生与课程组合。端到端新推荐中未评价的课程还需补充盲评。这 600 条记录不等于 600 个独立学生。

### 硬规则情境的覆盖

每类暂定 15 个基础情境，5 个开发、10 个测试，共 120 个。下列是覆盖标签，不是出现频率估计；挑战集的错误率不能直接解释成真实用户的线上错误率。

| 情境类型 | 必须覆盖的对照与反例 |
| --- | --- |
| 先修与学业记录 | 满足／不满足；AND/OR；最低成绩；记录不完整；考试或转学学分未知；在修与计划课程不同 |
| 专业限制与注册条件 | 符合／不符合；限制解除时间；需要许可；OPEN/FULL/Waitlist；不能把未来可能解除写成当前已可注册 |
| 开课与学期证据 | 官方确认开设／不开设；未来未公布；查询失败；历史开设只作参考；目标教授未知 |
| 时间和完整班次组合 | 讲座无冲突但 Dis 冲突；某班不行但替代班可行；全部组合不行；配对未知；TBA；Registrar 原始时间格式 |
| GE 与个人要求 | 官方类别已核实／未知；课程类别与个人抵扣不同；只补剩余 GE 但缺可信审计；在修预计覆盖与已完成不同 |
| 意图与条件强度 | “绝对不能”与“最好避免”；GPA 目标不自动变 GE-only；已完成 GE 不代表所有 GE 课程都不能考虑 |
| 会话与学期状态 | 明确日期优先；相关追问沿用；无关新问题重判；Week 8 边界；本学期与默认学期不同；默认标签只读 |
| 故障与输出一致性 | 工具超时、解析失败、证据矛盾；正文与实际班次一致；预算结束和 Continue；保存恢复；外部文本中的误导指令 |

无解、需要澄清和资料不足都应有专门案例；不能把 120 个情境全部设计成“总能找到三门课”。每个情境可以包含多个候选和多轮对话，提前标注关键断言以及整例通过条件。

开发与测试按底层情境、学生档案和证据来源分组：同一问题的改写、中英文版本、只改课程名或时间的近重复必须同组。最终测试应包含未见过的课程组合和条件组合。已修复 bug 的原例保留在回归集，不作为独立泛化证据的唯一来源。

### 硬标签如何产生

1. 从官方课程目录、目标学期完整课表、限制说明及必要的学业证据建立来源快照，保存 URL、采集时间、适用学期或学年、原文片段和文件哈希。
2. 为每个案例写清输入、学生资料完整程度、硬条件、可行候选、不可行原因、未知项和预期动作。
3. 两名标注者依据原始资料独立判定；记录初始一致率和分歧，由双方或第三人仲裁。软偏好不由标注者替学生判定。
4. 资格真值不能直接复制系统 Validator 的输出，否则系统与“答案”可能共享同一个错误。
5. 无法获得事实证据时标 U。问卷自报“GE 都完成了”或缺少某门已修课，都不能自动获得可信审计或完整学业记录标记。

可在合成测试中明确构造可信、完整的学业资料，检验已知条件下的功能；其结果单列为合成情境结果，不能证明真实学生审计接口已经接通。公开资料回放、合成数据、真实学生自报与已核实记录分别标明来源。

学期案例按 [term-rules.md](term-rules.md) 的产品规则标注，固定美西评估时钟，区分 `current_term`、`default_term`、`query_terms`、`recent_query_focus` 和历史参考。已有缺口是待检测对象，不能把当前错误输出写进正确答案。

## 四 可直接试用的问卷

开头说明：“本调查用于评估选课推荐工具。请不要填写姓名、学号或账户密码。不确定的信息可以填写不知道。请分别说明已经完成、正在修读和仅计划修读的课程。”

### 推荐前资料

| 题目 | 回答形式 | 是否给系统 |
| --- | --- | --- |
| 你的专业、第二专业是什么？ | 选择或填写 | 是 |
| 你是几年级，是否为转学生？ | 选择 | 是 |
| 本次规划哪个学期？ | 明确年份和季度 | 是 |
| 已完成、在修和计划课程分别有哪些？哪些考试或转学学分已确认？ | 分栏；允许未知 | 是 |
| 本次最主要的选课目标是什么？ | 最多三项排序：专业要求、GE、兴趣、控制负担、历史给分、职业准备等 | 是 |
| 有哪些绝对不能违反的条件？ | 不可上课时间、已有固定课程、其他条件；无则填无 | 是 |
| 哪些条件只是尽量满足？ | 避早课、少去学校、兴趣领域、授课方式等，按重要性排序 | 是 |
| 你确认还有哪些个人学业要求？依据是什么？ | 已核实／自报／未知分开 | 是，但仍按来源核验 |
| 使用工具前，你原本考虑哪些课程？为什么？ | 最多五门，可空白 | 否，保留作为评价参考 |
| 你对这些课程和学校选课规则有多熟悉？ | 1–5 分 | 仅作分析分组 |

不强制收集 GPA 或原始成绩单。仅在先修判断确实需要时收对应成绩或确认状态；保留匿名 ID，个人资料与可公开的合成案例分开存放。系统目前不支持的硬条件仍保留在输入与标签中，正确行为可为说明能力边界并澄清，不能静默删除条件。

### 独立课程评价

在查看任何方法的输出前，研究者依据官方目录和学生目标选定约 20 门候选，包含直接匹配、合理替代和部分不那么匹配的课程。固定候选排序实验优先使用已独立核实可行的课程；若不足 20 门，记录真实数量，不为凑数加入不可行课程。

所有方法使用相同候选。逐门展示中性的课程简介、学分、已核实的授课时间和方式及相关证据。历史 A 率或 RMP 如被用于推荐，给学生的中性资料也应采用相同来源和口径。随机排列课程，隐藏方法名称、推荐分和系统生成的理由。

每门课程回答：

1. “基于以上资料，这门课对你本次选课目标有多大吸引力？”0 不考虑；1 勉强考虑；2 愿意考虑；3 很想选；U 资料不足或无法判断。
2. “主要原因是什么？”兴趣、学业目标、时间、负担、授课方式、历史给分、其他；可补充一句。
3. “以前是否知道这门课？”知道／不知道。

原本意向名单不是唯一正确答案。学生未写某门课可能是不了解；系统发现新的合适课程应能得到认可。

### 推荐后体验

把完整系统和主要基线的固定候选列表以随机 A/B 编号、相同版式和数量展示，随机先后顺序。每种方法固定展示第 1 次计划运行的结果，失败则如实显示未完成，不事后换成最好的一次。先评价课程列表，再评价解释，避免把解释流畅度当作推荐相关性。

- 哪组更符合本次目标？A／B／差不多／都不合适。
- 每组整体帮助程度是多少？1–5 分。
- 解释是否符合你提供的偏好和实际课程信息？1–5 分或无法判断。
- 是否发现原先不知道、现在愿意考虑的课程？指出课程。
- 是否发现明显错误或无法修读的推荐？指出原因，交事实标注者核验。

试调查以约 20–30 分钟为可接受负担的初始目标，实际耗时以 pilot 记录决定。体验评价安排在独立课程评分之后；新增课程采用同样的中性资料补充盲评。

## 五 两条实验分别回答什么

### 固定候选排序实验

为每名学生固定约 20 门已核实可行的候选及同一份证据，只比较推荐前三门的偏好匹配。K 暂定 3，与现有常见“三门推荐”任务一致；若导师更关心长列表，可在实验前统一改为 5。

| 方法 | 具体做法 | 回答的问题 |
| --- | --- | --- |
| A 随机基线 | 同一可行池随机选三门，离线运行 20 个固定种子后取平均 | 系统是否优于随机选择 |
| B 固定评分基线 | 使用现有 A 率与 RMP 排名，冻结权重及缺失处理，直接取前三门 | LLM 选择和偏好理解是否超过现有固定评分 |
| C 完整推荐方法 | 保留现有意图、选择和出卡流程，但候选入口限制为相同候选集和证据 | 当前方法在可比条件下的偏好表现 |

随机方法不调用 LLM。B 使用真实已有评分，不称其为“热门课基线”，因为目前没有独立热门度真值。C 所需候选回放或限制入口需要在评测运行器中实现；若仅调用底层 `rank_candidates`，结果应称排序组件实验，不能称完整网站端到端结果。

学生评分和原本意向课程名单不得提供给各方法。不能按学生事后评分挑候选，也不能让 C 看到基线看不到的额外目录、成绩或评价信息。

### 完整网站端到端实验

输入学生资料和自然语言要求，通过真实 `/api/chat/stream` 让系统自主解析、检索、预筛、调用工具和生成正文与卡片。此轨道不限制到那 20 门课，检查完整链路是否遗漏候选、推荐不可行课程或错误解释证据。

固定外部数据响应进行可重复的主实验，但保留真实模型调用。保存原始 SSE、工具轨迹、最终正文、卡片、班号、预筛报告、澄清和错误。受限快照中缺失的数据返回未知，不能伪装成官方未开课。模型可查询的信息只来自指定评估时刻已可获得的资料。

对于候选池外的新推荐，先收集全部计划运行的输出，再去重、隐藏来源和排名，以随机顺序及中性资料补充学生评分；完成后才展示推荐列表和解释。研究者独立核验可行性，报告输出质量与联合命中。此轨道**不声称得到了整个 UCI 目录的真实偏好召回率**。另可统计原先标注的相关候选有多少被检索、保留和最终选中，用于定位漏检、误删和排序问题，但标明其分母是已知相关集合。

首版端到端轨道只评 C 的绝对表现，固定池内 A/B 的分数不作为其直接对照。若要声称完整网站的联合命中优于其他方法，须另加同全目录、同证据和预算的端到端基线。

需要研究模块贡献时，再增加相同模型、工具和预算下的消融实验。直接关闭开关可能同时改变检索截断、展示和门禁，不能直接把结果解释为单独某个排序模块的因果贡献；做单模块对照时须保持候选范围和其他行为一致。

## 六 指标和计算口径

### 硬指标

| 指标 | 计算方式 | 防止的误读 |
| --- | --- | --- |
| 明确违规推荐率 | 总体 F 的正式推荐数 ÷ 正式推荐总数 | 零违规不等于全都已核实 |
| 未核实或附条件占比 | 总体 U/C 的正式推荐数 ÷ 正式推荐总数，并分别列 U 与 C | 未知不能混成可选 |
| 已核实可行占比 | 总体 T 的正式推荐数 ÷ 正式推荐总数 | 表示证据覆盖下的可行性，不是注册成功率 |
| 案例行为通过率 | 满足全部预设关键断言的案例数 ÷ 全部案例数 | 澄清、无解说明和错误处理也可被评价 |
| 可行推荐覆盖率 | 在资料充分且独立确认存在可行候选的案例中，至少给出一门 T 推荐的案例数 ÷ 该类案例数 | 一律拒答不能获得有效性满分 |
| 完成程度 | 返回的不同课程数、已核实可行数与要求 K 同时报 | 一门安全推荐不能冒充完成三门任务 |

没有正式推荐时，前三个项目级比例为 N/A，保留该案例参与行为通过率、覆盖率及任务完成率。服务商 402、工具超时和程序报错不自动算正确拒答；独立标记为运行失败，计入全体请求的完成率，另报正常运行条件下的语义结果。

同时统计已核实的教授、学期、GE、时间、成绩范围等关键事实是否被正文和卡片正确表达，报告“含至少一处关键无依据断言的回答数 ÷ 已完成回答数”，并列错误类型。中间计划正确但最终答案说错仍为失败。

若导师需要混淆矩阵，增加一个**候选资格筛选任务**：正类定义为独立真值 T，预测正类定义为系统明确判可行；负类为真值 F，预测负类为系统明确判不可行。TP 是正确放行，FP 是错放不可行候选，FN 是错删可行候选，TN 是正确排除。预测未知不硬塞为负类，另报判定覆盖率和弃判数量；矩阵仅覆盖真值 T/F 且系统作明确判断的子集。

筛选 Precision = TP/(TP+FP)，筛选 Recall = TP/(TP+FN)。必须与判定覆盖率一起解释；它们与下面的 Top K 偏好指标是不同任务。资料不全时保留候选等待核实，不应直接视为“系统已判可行”。

### 软指标

在固定候选实验中，先定义学生的已评价相关集合 R：候选中评分为 2 或 3 的课程。只取原始展示顺序的前三个位置；重复课程不能重复命中，也不从第四名补位。少于三门时保留空槽。

- **Precision@3** = 前三位置中不同相关课程数 ÷ 3。回答“推荐出来的三门里，有几门学生愿意考虑”。
- **Recall@3** = 前三位置中不同相关课程数 ÷ 已评价候选池内相关课程总数。回答“这组已评价好课中找到了多少”。R 为空时为 N/A，并报告这类学生人数。
- **NDCG@3** 可作为次要排序指标，使用 0–3 分评价是否把更想选的课程排在前面；第一版不必把它列为主要结论。

示例：20 门候选中学生评价有 6 门愿意考虑，系统前三门命中 2 门，则 Precision@3 = 2/3，Recall@3 = 2/6。不能说召回了整个学校好课的三分之一。

U 不当作 0。优先用相同中性资料补充评价；仍无法判断时，报告标签覆盖率。若前三位置中有 h 门已知相关、u 门未评价，则 Precision@3 报范围 `[h/3, (h+u)/3]`；h、u 均只计算不同课程的首次出现，重复和空槽不增加上界。不能只挑可评价的输出计算高分。Recall 仅对已评价候选集合计算，并在名称和表中注明范围；不外推到含未知标签的完整候选池。NDCG 在标签不完整时不报完整池点估计。

推荐指标采用标准 Top K 思路，固定 K 和少返回时分母的处理可参考 [Microsoft Recommenders 评估文档](https://recommenders-team.github.io/recommenders/evaluation.html)。

### 联合指标和体验指标

**可行且合意命中@3 = 前三位置中同时为总体 T 且学生评分至少为 2 的不同课程数 ÷ 3。** 用于完整网站实验，也同时报告未知项和可判断覆盖率。U/C 或偏好未知的项目不计为已确认联合命中，但分别保留状态，不能据此断言学生不喜欢。若前三项都不可判，报告已确认命中下界和未判数量。

例如三门都很有吸引力，但一门先修不满足、一门时间未知，只有一门被证实可行，则已确认联合命中为 1/3。单看偏好得到的高分不能抵消硬性错误。

体验次要指标包括 A/B 列表偏好、有帮助程度、发现新课程比例，以及解释是否符合实际信息。另记录请求完成率、延迟中位数及 P95、供应商实际模型 usage 和费用；工具调用尝试数与实际外网请求数分开。现有日志包含本地字符估算 token 和按配置价格估算的费用，运行器需另采集供应商实际 usage；无法取得时标 unavailable，估算值附方法单列，不能混称真实用量或账单费用。

## 七 如何开展测试

1. **先定口径。** 与导师确认硬真值、正式推荐和待核实候选的边界、K、相关阈值、主要指标与研究范围。先固定评价规则，再看正式测试结果。
2. **做小规模 pilot。** 用开发集中的约 10–20 个情境及 5–10 名学生走通采集、标注、运行和评分；测量单例耗时、费用、问卷负担和未知比例。
3. **完善开发集。** 用 40 个开发情境修改运行器和系统；验证来源快照、课程归一化、班次组合与标签是否一致。真实学生自报不能被运行器自动改成权威记录。
4. **冻结版本与最终测试。** 记录代码提交及未提交改动快照哈希、模型、提示词哈希、两个开关、权重、温度、预算、工具版本、学期、时钟和来源快照。当前工作区存在未提交改动，单记 Git commit 不足以复现。清空评测身份的会话与记忆，禁止不同学生互相污染。
5. **运行封存硬规则集。** 80 个基础案例每例运行 3 次，固定配置且使用独立会话；多轮案例内部保持连续。记录全部失败与部分输出，不能挑表现最好的一次。
6. **运行学生实验。** 30 名新学生先提供资料与独立课程评分，再对同一候选运行 A/B/C；C 每学生 3 次。再跑完整网站轨道每学生 3 次，补充池外课程盲评，并完成列表体验比较。
7. **做实时核验和少量浏览器验收。** 实时子集使用实际外部来源，保存当次证据并解释与回放的差异；浏览器检查正文、卡片、Continue、课表和刷新恢复是否一致。实时结果与固定回放分开报告。
8. **分析再改进。** 先报告封存结果，再按意图、学期、检索、过滤、排序、配对、表达、数据和运行故障归因。针对测试失败修改后，称为该测试集上的改进结果；独立结论需新的保留案例或新一轮学生验证。

成本量级：上述封存实验中，C 方法约 `80×3 + 30×3 + 30×3 = 420` 次案例或会话运行，另有开发和实时核验。多轮、Continue 和重试会增加 HTTP 请求，一次请求还可能有多次模型调用；420 不是 HTTP 请求数或模型调用数。先用 pilot 测可取得的实际用量、估算费用和 P95 耗时，再决定是否缩小重复次数或把重复先限于预先随机抽定的子集；不能看完结果后只重复失败或成功案例来改善统计。

工程回归应在正式实验前完成。它是运行前提，不替代真实模型与学生评测。可复用的离线入口见附录；本讨论稿没有执行这些命令或发送收费模型请求。

## 八 结果如何报告

主结果按全部计划运行计算：运行失败按空列表计 Precision@3 和已确认联合命中 0；有相关标签时 Recall 也计 0。R 本来为空等标签不适用情况仍为 N/A，并单列数量。另报正常完成运行的条件性结果及完成率，不能只删掉失败运行后平均。

每名学生先对其重复运行取平均，再对学生取平均，比较同一学生在不同方法下的差值。硬规则也按基础情境聚合；不能把三次运行或十个改写当成多个独立学生或情境。报告分子、分母、缺失、运行失败和每组人数。

在样本允许时，按学生整体重采样估计偏好指标及方法差值的置信区间；硬规则按独立情境组处理。30 名学生用于探索，专业与年级子组很小，优先作描述分析。正式显著性研究的样本量根据 pilot 的变异、希望检测的差异与导师要求确定。

固定候选排序的比较表：

| 方法 | 偏好 Precision@3 | 已评价池 Recall@3 | 标签覆盖率 |
| --- | --- | --- | --- |
| A 随机基线 | 待测 | 待测 | 待测 |
| B 固定评分 | 待测 | 待测 | 待测 |
| C 完整方法的固定池版本 | 待测 | 待测 | 待测 |

硬规则挑战集和完整网站分别填写以下成绩单，标出各自案例数：

| 指标 | 分子和分母 | 结果 |
| --- | --- | --- |
| 案例行为通过率 | 通过案例／全部案例 | 待测 |
| 明确违规推荐率 | F 项／正式推荐项 | 待测 |
| 未核实与附条件占比 | U 项、C 项／正式推荐项 | 待测 |
| 可行推荐覆盖率 | 有 T 推荐案例／资料充分且有可行候选案例 | 待测 |
| 可行且合意命中@3 | 按学生聚合；硬规则集没有个人偏好标签时填 N/A | 待测 |
| 请求完成率与 P95 延迟 | 全部请求；另列故障类型 | 待测 |

不把三条轨道不同的分母混成一个总分。例如，只做排序的随机方法没有独立的硬行为通过率，应填 N/A，而非 100%。

建议验收方向是：封存集没有已知严重违规，系统对未知处理符合规范；固定池偏好相较主要基线有实际提升；完整网站有足够的可行且合意命中、覆盖和完成率。具体覆盖率、延迟与最小有意义提升在 pilot 后、封存前确定。“样本中零例严重违规”只描述该测试，不保证所有真实场景零风险。

## 九 与导师优先讨论的决定

1. 论文或项目主要贡献更偏规则可靠性、偏好推荐，还是两者联合？确定一个主要结论，避免指标很多却研究问题模糊。
2. 是否接受硬真值 T/F/U/C、系统行为 Pass/Fail 的区分？如何定义正式推荐与条件参考？
3. 第一版限定哪些专业、哪些学期和哪些选课目标？个人毕业审计是否作为本阶段必须实现的能力，还是评价其缺证据边界？
4. 是否采用“120 个硬情境、5–10 人 pilot、30 名新测试学生、每人约 20 门候选、Top 3”的探索规模？谁能协助独立事实标注？
5. 固定评分作为主要基线是否足够？需要验证的是完整系统增益，还是某个模块的单独增益？
6. 根据 pilot 的成本和不确定性，正式实验需要多少学生与重复次数？预先约定主要指标与验收门槛。
